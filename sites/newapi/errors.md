# 错误码对照

下面的报错文案全部来自 xm.solov.cc 的真实日志，按**文案**查最准（同一句话有时会带不同的状态码）。

::: tip 看不到具体报错怎么办
流式输出（大部分客户端默认开启）出错时，客户端往往只提示"连接中断""流解析失败""unexpected EOF"，不显示真正的原因。这时请登录 [日志](https://xm.solov.cc/usage-logs)，找到对应的那次请求，里面有完整的错误文案。本页内容以那里显示的文案为准。

报错里 `(request id: …)` 那一串是这次请求的编号，对你没用处，但**联系客服时请一起发过来**，我们靠它定位问题。
:::

::: warning 这几种错误重试没有用
`Invalid token`、`用户额度不足`、`预扣费额度失败`、`insufficient balance`、`system disk overloaded`。它们要么需要你改配置或充值，要么是我们这边的问题，脚本自动重试只会一直失败，还会刷满你的日志。
:::

## 令牌与余额

| 你看到的文案 | 状态码 | 原因 | 怎么办 |
|---|---|---|---|
| `Invalid token` | 401 | 令牌没通过校验。这一句涵盖所有鉴权失败：复制错了、多了空格或换行、令牌已被删除或重建、`Authorization` 头少写 `Bearer `、把网页登录密码当成了 API 令牌 | ① 到[令牌页](https://xm.solov.cc/keys)重新点"复制"，别手打；② 粘贴后确认前后没有空格和换行；③ 确认这条令牌还在列表里且状态是启用；④ 客户端如果有单独的 Bearer 选项，不要重复填；⑤ **改完之前先把客户端停掉**，错误的令牌会被自动重试上百次 |
| `用户额度不足, 剩余额度: ＄0.000000` | 403 | 账户余额用完了 | 到[钱包](https://xm.solov.cc/wallet)充值，到账后即可继续 |
| `用户额度不足, 剩余额度: ＄-0.037450`（负数） | 403 | 余额已透支。长请求会先按上限扣费，结算后可能出现小额负数 | 充值补正即可，负的部分会自动抵扣 |
| `预扣费额度失败, 用户剩余额度: ＄0.033968, 需要预扣费额度: ＄0.568120` | 403 | **余额还有，但不够这次请求的预估上限。** 本站在发起请求前会按"最坏情况"先冻结一笔额度，结束后多退少补。所以余额只剩几分钱时，长上下文请求依然会被拦下 | ① 充值；② 或临时缩短对话上下文、调小 `max_tokens`，让预估金额降下来。**这不是系统算错账，反复重试同样会被拦** |
| `insufficient balance` / `Insufficient account balance` | 403 | **这条不是你的余额问题**，是上游供应商账户欠费，报错被原样转发给了你 | 你充值没有用。先换一个模型试试，并联系[客服](/contact)反馈，我们会切换渠道 |

## 分组与模型

| 你看到的文案 | 状态码 | 原因 | 怎么办 |
|---|---|---|---|
| `No available accounts: no available accounts` | 503 | 你请求的模型当前没有可用的上游账号（多发生在 Claude 系模型） | ① 等几分钟重试；② 换一个同档次的模型；③ 超过十几分钟不恢复请联系客服。这不是你的账号或令牌问题 |
| `No available compatible accounts` | 503 | 同上，特指绘图 / 多模态这类需要专门渠道的模型 | 稍后重试，或改用其他绘图模型 |
| `All credentials for model xxx are cooling down`（可能带 `reset_time: 121h11m52s`） | 429 | 这个模型的上游凭证全部进入冷却。**那个几十上百小时的 `reset_time` 是上游给的窗口，不代表你要等那么久**，我们会持续补充可用凭证 | 换一个模型继续用，不要盯着这个模型重试，过一阵再回来 |
| `channel does not support /v1/xxx` | 500 | 你调的接口，当前分配到的渠道不支持（例如把搜索类接口打到了只支持对话的渠道） | 确认客户端确实需要这个接口；换个模型试试；仍不行请把接口路径发给客服 |
| 客户端提示"模型不存在 / 无权使用该模型" | — | 模型名拼错，或你的分组不含这个模型 | 到[定价页](https://xm.solov.cc/pricing)复制准确的模型名；确认令牌分组包含该模型 |

## 频率与并发

| 你看到的文案 | 状态码 | 原因 | 怎么办 |
|---|---|---|---|
| `Too Many Requests` | 429 | 请求发得太密，触发限流 | 等几秒再发，大部分客户端会自动退避 |
| `Upstream rate limit exceeded, please retry later` | 429 | 上游服务商的限流，不是本站的限制 | 等一会儿重试，或换模型分流 |
| `The usage limit has been reached` | 429 | 上游账号触到周期用量上限（不是你的余额，也不是本站限制） | 换模型继续用，或稍后再试 |
| `Too many pending requests, please retry later` | 429 | 排队中的请求太多 | 减少同时发起的并发数 |

::: tip
限流类报错在最近的统计里只占全部请求的 0.16%。如果你频繁遇到，多半是客户端的并发或自动重试开得太激进，建议调低。
:::

## 上游故障（等一会再试）

| 你看到的文案 | 状态码 | 原因 | 怎么办 |
|---|---|---|---|
| `Service temporarily unavailable` | 503 | 上游服务临时中断，这是最常见的一类故障，且往往集中在个别时段 | ① 等 1–3 分钟重试，多数能自行恢复；② 换一个模型往往能立刻绕开；③ 持续十几分钟且多个模型都不行，说明是较大范围的上游故障，看公告或问客服，不用反复重试 |
| `Upstream service temporarily unavailable` / `Upstream request failed` | 502 | 上游没有正常应答 | 同上，稍后重试或换模型 |
| `upstream error: do request failed` | 500 | 本站连不上上游（网络层失败） | 稍后重试；持续出现请联系客服 |
| `Upstream returned HTTP 403 Forbidden` | 400 | 上游拒绝了这次请求 | 换个模型试试；反复出现请把 request id 发给客服 |
| `system disk overloaded (current: 96.7%, threshold: 95%)` | 503 | **本站服务器磁盘占用超过阈值，主动进入保护性拒服务。** 这是我们的运维问题，与你的账号、令牌、余额都无关 | 你无需做任何操作，等待恢复或联系客服确认进度。看到这条**请不要重试**，重试只会加重负载 |

## 请求内容问题

| 你看到的文案 | 状态码 | 原因 | 怎么办 |
|---|---|---|---|
| `Missing required parameter: 'xxx'.` | 400 | 请求体缺了必填字段。基本只出现在自己写脚本或用 curl 手调接口的场景 | 对照接口文档补上。用现成客户端一般不会遇到 |
| 其他 `invalid_request_error` 提示 | 400 | 请求格式不合法（JSON 写错、字段类型不对） | 检查 JSON 是否合法，`model` 名称与 `messages` 结构是否符合规范 |

## 地址填错

这一类**不会**返回 404，因为请求根本没打到 API 接口上，而是打到了控制台网页：

| 你看到的现象 | 原因 | 怎么办 |
|---|---|---|
| "连接失败 / 无法访问 / 请求超时" | 域名写错、协议写成了 `http://`、或被本地网络拦截 | 确认地址是 `https://xm.solov.cc`，注意是 **https** |
| "返回了 HTML / JSON 解析失败 / Unexpected token `<`" | **Base URL 少写或多写了路径**，请求打到了网页，服务器把 HTML 返回给了客户端 | 有的客户端要填到 `https://xm.solov.cc/v1`（Cline、OpenCode、Hermes），有的只填 `https://xm.solov.cc`（Codex、Claude Code、Gemini CLI，它们自己会补路径）。**两边都写 `/v1` 会变成 `/v1/v1/…`，同样出错**，对照对应客户端的教程逐字核对 |
| 404 / Not Found | 接口路径不对 | 不要自己拼接口路径，用客户端的默认配置 |

::: warning 客服在后台查不到你的请求？
地址填错的请求不会进入本站的 API 日志，所以客服确实看不到记录。如果客服说"没看到你的请求"，通常就是地址填错了，请优先按上面三条自查。
:::

## 还是解决不了

把**完整报错文案**（含 request id）、使用的模型和大致时间发给[客服](/contact)（每日 9:00–23:00），我们会在日志里定位这次请求。
