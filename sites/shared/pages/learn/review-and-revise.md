# 检查结果与继续修改

能得到输出不等于已经完成任务。本课适用于文案、资料整理、文件处理和简单项目协作。

## 1. 先把“完成”写成可检查的标准

使用上一课的虚构文具店案例：正文长度符合要求；18 元、80 页、三种颜色没有变化；没有编造库存、运费或认证；输出文件存在；原始资料未被覆盖。

换成自己的任务时，也要先写验收标准。无法检查的“高级一点”“全部弄好”容易让双方对完成状态产生不同理解。

## 2. 把结果分成四类检查

| 类别 | 要检查的问题 |
| --- | --- |
| 事实 | 内容是材料提供的、合理推断的，还是没有依据的？ |
| 范围 | 有没有修改不该改的部分或使用不需要的权限？ |
| 交付 | 文件、页面、表格是否真实存在且能打开？ |
| 状态 | 哪些已经验证，哪些只是建议、草稿或待确认？ |

输出中的引用要能追溯到实际来源。运行或测试成功应有可检查的结果，不能把“建议运行以下命令”当成“测试已经通过”。

## 3. 一次修改一个明确范围

```text
保留当前标题和所有数字。
只改第二段，让读者更容易理解。
不要重新生成其他段落，不新增卖点。
完成后列出本次改动，以及仍然需要我确认的内容。
```

对文件任务，补充准确文件名、允许变化的区域及禁止覆盖的文件。修改前后做比较，确认它没有顺手更改无关部分。

## 4. 什么时候继续当前对话，什么时候整理后重开

围绕同一份材料的小修改，可以继续当前对话。材料换了、任务目标变了、上下文太长或多次产生相同误解时，先整理一份交接摘要，再开新对话。

```text
请给出交接摘要：
1. 当前目标与不可改变的约束。
2. 实际输入文件和已生成的输出文件。
3. 已完成且有证据的事项。
4. 尚未完成、未经验证及存在争议的事项。
5. 下一步最小可执行任务。
不要把计划写成完成，不要包含密钥或密码。
```

摘要也需要人工核对，特别是版本、地址、文件位置与待办状态。

## 5. 用版本保留退路

重要结果另存新版本，记录改动原因。文案可以用 v1/v2，项目文件可以使用已有版本管理方式；没有版本管理经验时先做独立副本，不要照抄强制回退命令。

如果涉及付款、发送信息、公开发布或删除，先检查目标和后果，再决定是否授权。技术上执行成功，不等于内容已被你批准对外使用。

## 一份可复用的验收请求

```text
请对照我最初的要求逐项自查：
要求｜实际结果｜核对依据｜未完成项。
对没有检查过的部分写“未验证”。
不要为了通过检查而补造运行记录或来源。
```

助手自查可以帮助发现遗漏，但不能替代你对最终交付的检查。
