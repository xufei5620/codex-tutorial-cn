## 0. 先读这三段

### 0.1 你的角色与本轮目标

教程里所有关于产品的说法，目前都只有「官方文档」这一个依据。本轮的目标是**把它们放到真实电脑上逐步走一遍**：
每一步是否能照做、屏幕上实际显示什么、教程哪里说错了或说含糊了；把观察结果记进仓库，据此修订正文，让下一版可以诚实地写上「已在 Windows / macOS 实测」。

你不是在写新章节，也不是在重新设计教程。你是在**验证并纠正**已有内容。

### 0.2 分工：你能自己做的，和必须请用户做的

| 你自己就能做 | 必须请用户用眼睛和手完成 |
|---|---|
| 读仓库、改 `src/`、跑 `build.py` / `check.py`、提交推送 | 安装应用、登录账号 |
| 检查本机文件系统与配置：`~/.codex/`、`~/.agents/skills/`、日志目录是否存在、里面有什么 | 阅读并转述界面上的文字：按钮名、菜单项、弹窗文案 |
| 观察你自己的行为：这次操作弹没弹审批、审批弹窗上写了什么、你被限制在哪个文件夹 | 点审批、切换权限模式、打开设置页 |
| 执行教程里的请求（粘贴文字、整理文件夹、建定时任务）并保存输出 | 截图（按 §2.2 的脱敏规则） |

工作节奏：**每个测试项由你发起**——「请你做 X，然后告诉我看到了什么」——用户回答后你把结果记入验证记录，再进下一项。用户开启了 Computer Use 的话你可以自己操作界面，但证据仍然要截图。

### 0.3 实测期间的红线

1. 权限模式始终 **Ask for approval**。测试中任何一步都不切到 Approve for me 或 Full access，包括「为了省事」。
2. 只在 **§3.3 的练习文件夹副本**里动文件。不碰桌面、文稿、下载等真实文件夹的其他内容。
3. 只用仓库里的虚构素材；对话里不出现真实的人名、公司、客户、账号、邮箱。
4. **不删除任何文件**。教程里出现「删除」字样的地方，测试时也一律拒绝，记录弹窗即可。
5. 插件测试只用专门注册的测试账号；测完立即卸载插件、断开授权（§4 ch06）。Skill 测试建的文件夹测完删掉。定时任务测完立即暂停或归档。
6. 消耗额度的事先问用户：图片生成（PRM-COM-0006）默认**不实际生成**，只跑到「写清需求」这一步。
7. 不改 `main`，不打 tag，不发 Release。不手改根目录生成物。

## 3. 环境准备

### 3.1 需要的东西

- 一台 Windows 11（Windows 10 也行，记清版本）和一台 macOS 14 或更新的电脑。只有一台就先测一台，记录里平台列写清楚，另一列写 `unverified（无设备）`。
- ChatGPT 桌面应用**最新版**（不要装成 ChatGPT Classic）。记录版本号：在设置里找「关于 / About」或版本信息；找不到就截设置页首屏。
- 一个 ChatGPT 账号。**第 6 章插件测试请用专门注册的测试账号**，不要拿用户的主账号给第三方授权。记录账号类型（Free / Go / Plus / Pro…），因为不同套餐的额度和功能可能不同。
- 网络可用。地区限制：如果登录时出现地区不支持的提示，停下并如实记录（这本身就是 10.2 的一个条目）。

### 3.2 每次开始前记录的环境信息

系统版本、应用版本、账号类型、日期、语言设置（界面是英文还是中文）。写在验证记录的「环境」列，同一天同一台机器可以简写为一个环境编号（如 `W1`、`M1`）并在文件顶部定义。

### 3.3 准备练习素材

把仓库里的 `src/research/fixtures/练习-蓝溪整理` 和 `src/research/fixtures/练习-开学季` **复制**到桌面（保持文件夹名）。**每次测试前重新复制一份干净的**，被改乱了就删掉副本再复制。仓库里的原件不要交给 Codex 处理。

素材里全部是虚构数据；`练习-蓝溪整理/答案.md` 是第 8 章 8.6 的预期结果，只给你核对用，**复制到桌面时把它去掉**。

## 5. 实测结果怎么写回正文

三种结果，三种动作：

| 结果 | 动作 |
|---|---|
| **与教程一致** | 两个平台都确认 → 删掉「以实际为准」「推断」之类的保留语，改成肯定句。只测了一个平台 → 保留保留语，或写成「在 Windows 上实测为……」 |
| **与教程不一致** | 改成实际观察到的说法（界面英文名照抄，后附中文）；维护者信息块的验证状态写 `verification-failed → 已修订`；11.3 的 0.2.2 行里列出改了什么 |
| **无法验证** | 正文保持保留语不动；验证记录写 `unverified` 或 `unsupported` 和原因 |

写回时的规矩：

- 读者是零基础：短句、白话、不加新概念。不要因为你了解得多就把 CLI、config.toml 细节写进读者正文（第 7 章 7.6 已有的一句除外）；这些放 `notes.md`。
- 不改章节结构、不加减小节（导航与 id 会对不上）。要加内容就加在现有小节里。
- 每一处改动都能在验证记录里找到对应的测试项 ID。
- 界面文字随版本变化，所以写法上留一点余地：「目前叫 X」比「叫 X」更耐用。
- 维护者信息块「验证状态」写法示例：
  `Windows：verified（2026-09-10，应用 1.x.y，T03-01～07）；macOS：verified-with-limitations（2026-09-12，T03-03 第 3 步未能复现拖入提示）。`
  「模块 ID / 状态」行保持 `draft`；「复核日期」行追加「实测：日期」。
- 11.4 表：对应平台的「实测」列改成「是（日期）」；部分验证写「部分（日期）」。
- `chapters.json` 的 `status` 不动（仍是 `draft`；进入 `reviewed` 是另一条规则，见 `src/maintainer/maintenance-release.html`）。
- 本轮结束时：`chapters.json` 版本改 `0.2.2`、日期改当天；11.3 加一行 `0.2.2`；`build.py` 的 `readme()` 里那句「均为「草稿」：依据官方文档撰写，尚未在真实电脑上逐步实测」按实际改写。

## 6. Git 流程

```
git fetch origin
git checkout v0.2.2            # 已存在；只在这个分支上工作
# …改 src/…
python3 src/build.py && python3 src/check.py && git status
git add -A
git commit -m "test: ch03 Windows 实测 —— 修订 3.1/3.4/3.7，验证记录 T03-01～07"
git push -u origin v0.2.2
```

- 每章一个提交（大章可以拆成几个），提交信息前缀 `test:`；纯修订正文用 `docs:`；改 build.py/check.py 用 `build:`。
- 提交前看一眼 `git diff --stat`：只应有 `src/` 里你改的文件、`src/research/` 里的记录与证据，以及根目录生成物。证据文件先按 §2.2 脱敏再 add。
- 不 rebase、不 force push、不动 `main`、不打 tag。
- Windows 上的两个坑：仓库已用 `.gitattributes` 强制 LF、`build.py` 写文件固定 `\n`，所以生成物应当字节一致；如果 `git status` 显示大量生成物变化而你没改内容，先查换行符（`git config core.autocrlf` 建议在本仓库设为 `false`）。控制台中文乱码时设置环境变量 `PYTHONUTF8=1`。

## 9. 拿不准时的原则

- 教程与实际不一致 → 以实际为准改教程，但**先确认不是你操作走偏**（重做一次）。
- 官方文档与实际不一致 → 记录两者，正文按实际写并注明「官方文档描述与此不同」；这是登记表里 `conflictRule` 的要求（保留官方与实测两种证据，不宣称完全验证）。
- 一个功能在你的账号/地区/版本上看不到 → 判 `unsupported`，写清楚条件，不要写成「没有这个功能」。
- 拿不准要不要改正文 → 不改正文，只记验证记录，报告里列为「需要用户决定」。
- 任何要花钱、要授权第三方、要碰真实数据的步骤 → 停下问用户。
